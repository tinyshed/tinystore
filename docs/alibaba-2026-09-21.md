# Third corpus: the Alibaba cluster trace, and the first irregular timestamps

Ryzen 7 7700, Windows 11 host, Docker linux/amd64, Go 1.27.1, SQLite driver
1.59.0, klauspost/compress 1.19.0. Base codec `9e34181` plus the grid model of
[the NAB grid run](grid-2026-09-21.md), which lives only in `spike/`. Same
harness and same three-engine method as [the TSBS run](tsbs-2026-09-21.md).

## The corpus

[Alibaba Cluster Trace 2018](https://github.com/alibaba/clusterdata),
`machine_usage`, real production data rather than a generator:

```text
http://clusterdata2018pubcn.oss-cn-beijing.aliyuncs.com/machine_usage.tar.gz
1774523160 bytes
sha256 3e6ee87fd204bb85b9e234c5c75a5096580fdabc8f085b224033080090753a7a
8996532344 bytes of CSV, 246934820 rows, about 4000 machines over eight days
```

The selection rule is stated rather than convenient: machines whose numeric id
is a multiple of 16, samples strictly before trace second 172800, which is the
first two days.

```text
246934820 rows read
  2486377 rows selected
      248 machines, 1240 series, 12431885 samples
        0 duplicate timestamps, 0 rows with no value at all
```

Three things this corpus has that neither earlier one did:

**Irregular timestamps.** `386640, 386670, 386690, 386800, 386930` — steps of
30, 20, 110 and 130 seconds. NAB and TSBS were both perfectly regular, so until
now the timestamp path had never carried real weight.

**Real decimal floats from production.** `net_in=43.04`, `net_out=33.08` are
written with two decimals, the pattern that made the grid model win on NAB —
but here they come from a production trace rather than from 24 hand-picked NAB
series.

**Holes.** `m_1932,386640,41,92,,,43.04,33.08,5` has two empty columns.
`mem_gps` and `mpki` are absent throughout, which is why 248 machines give 1240
series and not 1736.

`bench/alibaba` selects and normalises, emitting influx line protocol so that
the same `bench/tsbs` converter and the same three-engine path serve this
corpus too.

**One property of the data had to be discovered rather than assumed.** The
converter first assumed each machine's rows form one contiguous block and
checked it; the check fired on `m_1936`. A machine's rows are scattered through
the file. Assuming otherwise would have produced series whose timestamps run
backwards and a measurement that looked fine.

## Absolute sizes, and all three engines exact this time

| Engine | Bytes | B/sample | Every float bit returned |
|---|---:|---:|:--|
| VictoriaMetrics, complete directory | 6338675 | **0.5099** | yes |
| TinyStore, complete SQLite file | 9224192 | 0.7420 | yes |
| Prometheus, two blocks | 10662738 | 0.8577 | yes |

| Part | Bytes | B/sample |
|---|---:|---:|
| VictoriaMetrics `data` | 3281982 | 0.2640 |
| VictoriaMetrics caches | 3056685 | 0.2459 |
| TinyStore payload | — | 0.4282 |
| TinyStore SQLite envelope | — | 0.3138 |
| Prometheus chunks | 9778628 | 0.7866 |
| Prometheus index | 883474 | 0.0711 |

**VictoriaMetrics returned all 12431885 values bit for bit on this corpus.**
That refines rather than contradicts [the TSBS finding](tsbs-2026-09-21.md),
where 147751 of its floats changed. VM stores a decimal representation of about
thirteen significant digits: it is exact for values that fit, and lossy for
values that do not. This corpus is two-decimal and integer throughout, so
nothing was lost. TSBS had values like `84.39234509132802`, so a great deal
was. The honest statement about VM is therefore neither "bit-exact" nor
"lossy" but **exact within about thirteen significant decimal digits**, which
is a contract, just not TinyStore's.

Prometheus returned every value in the checked window bit for bit. A whole
`promtool tsdb dump` of this corpus is tens of gigabytes of text, so the check
covers a stated window — 1767225600000 to 1767232800000 milliseconds, 468470
samples across all 1240 series — and the window is printed with the result.

So on this corpus the comparison is like for like on exactness, and
**TinyStore loses to VictoriaMetrics by 31%** while beating Prometheus by
13.5%. That is the opposite of the TSBS result, where TinyStore's payload was
19% below VM's data files. Two corpora, two directions; neither is the engine's
general standing.

## Where the difference is, and it is not the value codec

The payload splits by encoding each block twice: once with its real values and
once with a constant, which the value codec stores in no bytes at all. The
difference is the value stream.

| | TSBS | Alibaba |
|---|---:|---:|
| Blocks on a single timestamp step | 22220 of 22220, 100% | 9070 of 52395, **17.3%** |
| Payload | 0.5739 | 0.4241 |
| Timestamps and framing | 0.0349, 6.1% | **0.1898, 44.8%** |
| Values | 0.5389, 93.9% | 0.2343, 55.2% |

83% of this corpus's blocks are irregular, and timestamps go from a sixteenth
of the payload to nearly half of it. Per block that is about 8 bytes of
timestamps and header on TSBS against about 45 on Alibaba.

The value stream is the part that holds up. **TinyStore's values alone cost
0.2343 B/sample, which is below VictoriaMetrics' entire `data` footprint of
0.2640 for both timestamps and values.** Since our values already fit inside
VM's whole budget, none of the deficit can be attributed to the value codec:
the whole of it comes from the timestamp stream. That is an inference from two
measured numbers rather than a guess about VM's internals, and VM's own split
was not instrumented.

This is the first corpus that could have shown this, because it is the first
one whose timestamps are not on a fixed step.

## The envelope moved, exactly where cardinality predicted

Per b-tree from `dbstat`, page size 4096, after a truncate checkpoint, beside
the TSBS run:

| Object | TSBS B/sample | Alibaba B/sample |
|---|---:|---:|
| payloads | 0.6864 | 0.4797 |
| blocks | 0.2229 | **0.2422** |
| registry plus its index | **0.2245** | **0.0145** |
| series_state and series_due | 0.0193 | 0.0053 |
| sqlite_schema | 0.0008 | 0.0003 |
| Envelope total | 0.5764 | 0.3138 |

The label registry, the largest single item the TSBS run found, is **fifteen
times cheaper per sample here**. That is not a refutation of the TSBS finding
but its explanation: the registry's cost is per series, and TSBS has one series
for every 2520 samples where this corpus has one for every 10025. Two corpora
give two points on that curve and both are real.

The blocks table did not move: 0.2229 and 0.2422, about 57 bytes for a row
covering a nearly full block — 237 of a possible 240 samples here. **It is a
structural tax of roughly 0.24 B/sample that does not depend on the corpus**,
and it is now 77% of the envelope. Twelve columns of eight-byte integers and
reals per block is what that buys.

The next thing to attack is therefore the block row, not the registry and not
the page size. Narrowing it, or covering many blocks with one row, is the
lever — and covering many blocks with one row is exactly what the
[incremental BLOB probe](tsbs-2026-09-21.md) showed can now be read without
materialising the whole group.

## The grid model, on a third corpus

Chosen in **175 of 52395 blocks**, worth 0.02% of payload: 0.4283 to 0.4282.

This corpus was the fair test. Its floats are genuinely decimal, written with
two places, from production — the shape the model was built for. It still did
not pay, because the existing codec's own scaled-integer path already handles
two-decimal values, and what is left over is timestamps.

Three corpora: NAB 39%, TSBS 0.12%, Alibaba 0.02%. The model is a specialised
path for series whose decimals run deeper than the existing scaled path
reaches, not a general improvement. The selector declining it 52220 times out
of 52395 is the design working, not the model failing.

## Two numbers in the run output that should not be read at face value

`ENCODE control=1.34s learned-total=1.01s` is **not** a speedup. When a series'
first block declines the model, no later block in that series attempts it, so
the learned timer counts almost nothing; and the control is timed first, on
colder caches. It measures how often the model was skipped, not how fast it is.

`integers=0 floats=12431885` from the converter is meaningless on this corpus.
`bench/alibaba` emits values without influx's integer suffix, deliberately, so
each value keeps the exact text it was written with. The converter's
integer-versus-float counter therefore counts everything as float here.

## Not measured

Ingest throughput for any engine, WAL, retention, crash recovery, cold reads,
query latency, RSS, and any engine under a live scrape rather than a bulk
import. Prometheus' figure is two blocks produced by `promtool` with
`--max-block-duration=72h`, which it split at 18 and 30 hours; that is not what
its own compactor would have chosen. VictoriaMetrics' figure follows
`force_flush`, an asynchronous `force_merge` and a graceful shutdown, and is
not a certified compaction optimum. The 248-machine, two-day selection is a
subset: the trace's full eight days and 4000 machines were not measured, and
this corpus has low cardinality for its size, which is the opposite of TSBS
rather than a neutral choice.

## Reproduce

```powershell
./bench/run-alibaba.ps1
```

It verifies the archive against the hash above, extracts, selects, converts,
measures TinyStore, then VictoriaMetrics and Prometheus, and checks each
engine's round trip against the corpus. `-SkipEngines` stops after TinyStore.
The timestamp and value split is separate:

```powershell
docker run --rm -m 12g -v <repo>:/src -v <corpus>:/corpus -v dashbin-gocache:/go -w /src -e TINYSTORE_JSONL=/corpus/series.jsonl -e GOCACHE=/go/build-cache golang:1.27 go test ./spike -run '^TestTimestampAndValueShare$' -v -count=1
```

New code: `bench/alibaba`, `bench/run-alibaba.ps1`,
`spike/split_spike_test.go`, and window support in
`spike/engines_spike_test.go`. No root dependency and no released format
changed. `task lint`, `task test`, `task vuln`, `task fmt` and `task tidy`
pass.

Both PowerShell runners build docker's argument list as an array. Inline,
PowerShell splits `-in=/out/x.csv` into `-in=/out/x` and `.csv`, which silently
strips the extension from every path-shaped flag.

# Статус TinyStore для архитектурного ревью

Этот отчёт фиксирует состояние **до packed head**. Обновление рабочего engine
и новый TSBS-прогон находятся в [packed-head-2026-09-21.md](packed-head-2026-09-21.md):
TSBS теперь 1.078234 Б/сэмпл вместо приведённых ниже 2.509709. Старые результаты
сохранены как история; новый Alibaba-прогон пока не выполнен.

## Короткий ответ

**Полная целевая архитектура пока не реализована. Лучшие значения плотности
исследовательских прототипов рабочий движок пока не повторяет.**

Реализован первый сквозной metrics engine: Open → Ingest → Read → Maintain →
Close → повторный Open, с реальным SQLite-файлом, индексом labels, точным head,
запечатыванием, shared clocks, несколькими кодировками значений и retention.
Это уже код библиотеки, независимый от spike/, но ещё не весь продукт и не
основание заявлять производственное превосходство над VictoriaMetrics.

База репозитория — `9e34181`; реализация и исследовательские материалы находятся
в незакоммиченном рабочем дереве. Нового release/tag и подтверждённого CI этого
состояния нет. Ниже перечислены локально выполненные проверки.

## 1. Какие цифры относятся к чему

Все значения — байты на исходный сэмпл. Для TinyStore считаются целые SQLite
файлы. Для VM в основной колонке — ранее измеренный полный каталог, включая
кеши. Prometheus и VM в этом этапе заново не запускались.

| Корпус | Лучший исследовательский TinyStore | Реальный metrics engine | VM, полный каталог | Prometheus |
|---|---:|---:|---:|---:|
| Alibaba, 12431885 сэмплов | **0.360776** | **0.733083** | 0.5099 | 0.8577 |
| TSBS, 5090400 сэмплов | **0.966387** | **2.509709** | 1.0774 | 1.6307 |

Уточнение TSBS: единый combined-прототип дал 0.970410; 0.966387 — предыдущий
лучший вариант с объединёнными payload. Это разные исследовательские layouts.
Рабочий engine использует отдельные внешние payload и собственные версии
директорий; он не побайтовая копия одного стенда.

| Реальный engine | Байт в файле | Полная проверка после переоткрытия |
|---|---:|---|
| Alibaba | 9113600 | все timestamps и float bits совпали |
| TSBS | 12775424 | все timestamps и float bits совпали |

Следствия:

- На Alibaba рабочий файл примерно на **43.8% больше VM**, и на **14.5% меньше
  ранее измеренного Prometheus**.
- На TSBS рабочий файл примерно на **133% больше VM** и на **54% больше
  Prometheus**.
- Фраза «мы обошли VM на Alibaba» применима только к ранее измеренному полному
  каталогу VM против исследовательского compacted-layout прототипа. Она не
  описывает текущий engine.
- Даже у прототипа VM без кешей компактнее: Alibaba data+metadata VM —
  3281990 байт, combined TinyStore — 4485120 байт.

## 2. Почему прототип и engine расходятся

Прототип напрямую создавал запечатанные объекты. Рабочий engine сначала
фиксирует изменяемый head, затем переносит только безопасный префикс. Он также
хранит postings, версии, фронтиры, миграции и другие служебные структуры.

Особенно показателен TSBS: 2020 серий по 2520 сэмплов. При такой загрузке
запечатываются 2400, а оставшиеся 120 на серию сохраняются в head. Это 242400
несжатых head-точек. Они не выбрасываются и не объявляются immutable ради
улучшения цифры файла.

Разложение реального TSBS-файла:

| Объект | Байт |
|---|---:|
| head | **6402048** |
| payloads | 3076096 |
| series | 1011712 |
| unique index серии | 1011712 |
| postings | 663552 |
| groups | 409600 |
| series_state | 77824 |
| series_due | 36864 |
| остальные b-tree из dbstat | 24576 |
| остаток полного файла сверх перечисленных dbstat-страниц | 61440 |
| **Всего** | **12775424** |

В частности, одна таблица head занимает примерно половину файла. Текущая
канонизация labels и её индекс также тяжелее компактного registry из стендов.
На TSBS фактически используется один shared clock.

Остаток в 61440 байт не приписан конкретной структуре: dbstat был снят до Close,
а физический размер — после него. Freelist для этого прогона отдельно не записан.
Остаток включён в итог, а не вычтен из размера engine.

Для Alibaba точное разложение этого конкретного engine-прогона по объектам не
сохранено, поэтому приписывать весь разрыв одному head было бы предположением.
Для обоих корпусов одинаково неверно вычитать эти обязательные части из размера
файла и объявлять оставшееся полноценным engine scoreboard.

## 3. Что действительно реализовано

### Границы

- `metrics/`: публичные типы и жизненный цикл метрик.
- `internal/sqlite/`: соединения, query-only readers, writer, транзакции,
  идентичность файла и проверяемые миграции.
- `codec/`: существующий независимо используемый block codec.
- `spike/`: исторические исследовательские стенды, не зависимость engine.

Records, KV и SQL mapper не создавались как пустые каркасы и не участвуют в
работе метрик. Общего универсального object/kernel framework нет.

### Запись и запросы

- Атомарный ограниченный batch, включая создание серий и postings.
- Канонические labels, equality matchers, cardinality и размерные ограничения.
- Битовое хранение float в head, включая `-0`, NaN payloads и бесконечности.
- Последнее значение выигрывает для дубликата timestamp в изменяемом head.
- Отказ на записи за retention cutoff или за persisted sealed frontier.
- Чтение `[from,to)` с логическим отсечением retention, без скрытого downsampling.
- Registry, head, directories, clocks и payload читаются в одном snapshot.
  Значения декодируются после его закрытия.
- Отдельные лимиты matched series, bytes, blocks, decoded/output samples и
  времени snapshot; ошибка не сопровождается частичным ответом.
- Close прекращает приём операций и дожидается уже допущенных запросов.

### Кодирование и layout

- Независимые микроблоки до 240 сэмплов, группы до 32 слотов.
- Ограничение event-time span блока и размерные пределы объектов.
- Shared clocks с проверкой хеша и полного совпадения; regular clock, quantum
  deltas, runs, dominant cadence с исключениями.
- Constant без value payload; change events; обычный integer/scaled/XOR/raw
  codec; decimal grid с точными IEEE-поправками и remembered scale hint.
- Residual modes: zero, sign bitmap, packed bitmap, fixed-width, sparse gaps,
  varints с необязательным zstd.
- Inline до 16 байт; внешние payload отдельно; неизменяемая allocation mask и
  отдельно изменяемая live mask.
- Компактные точные сводки, различение gauge/counter, increase/reset summary.
- Checksums, версии новых форматов, чтение старых директорий и миграция старого
  файла. Это новый production parser, не вызов test helper из spike/.

### Обслуживание

- Безопасный префикс определяется временем самой серии и lateness.
- Encoding выполняется вне writer; публикация проверяет version.
- Payloads, clock ownership, directory, удаление head и frontier меняются в
  одной транзакции.
- Ограниченный проход expiry, очистка quiet head, частичный live mask, last-owner
  clock deletion и восстановление due-записи после оживления пустой серии.
- Maintain вызывается явно приложением; фонового scheduler внутри пока нет.

## 4. Что ещё не реализовано или не доказано

| Работа | Статус |
|---|---|
| Packed mutable tail | отсутствует; head — точные отдельные строки |
| Merge/repack уже запечатанных маленьких групп | отсутствует |
| Подбор закрытия по стоимости SQLite-страниц | отсутствует; есть count/span/clock-byte пределы |
| Автоматическое переобучение grid hint | отсутствует |
| Aggregate/rate API | отсутствует; сводки записываются, наружу выдаётся raw |
| Несколько decode workers | отсутствуют; encoder отделён от одного decoder |
| Публичное удаление серии | отсутствует; пустая серия остаётся в cardinality |
| Background scheduler | отсутствует; Maintain — явный вызов |
| Records/KV/SQL/network service | не начинались |
| Steady-state WAL, RSS, cold reads, p95/p99 | не измерены для engine |
| Полная power-loss/crash matrix | не выполнена |

Общие clock объекты сейчас хранят полный временной контекст группы. Разделение
одинаковых относительных паттернов между разными абсолютными диапазонами не
введено. Восемь clock descriptors кешируются только внутри одного запроса.

Raw bit-exact не означает автоматически bit-exact SQL SUM/AVG: контракт
агрегаций требует отдельного решения об округлении, NaN, бесконечностях и порядке
сложения. Наличие сохранённой sum не заменяет этого решения.

## 5. Что проверено

Среда: Windows host, Ryzen 7 7700; Go 1.27.1; Linux Docker; modernc SQLite
1.59.0; klauspost/compress 1.19.0.

- Все обычные тесты с перемешанным порядком прошли на Windows.
- Все пакеты прошли `go test -race -shuffle=on ./...` в Linux.
- Lint, formatting, tidy обеих основных Go-модулей и govulncheck прошли.
- Новые binary readers прошли 15-секундный fuzz-прогон, около 119450 запусков,
  без найденных падений. Это ограниченный прогон, не исчерпывающее доказательство.
- Golden vectors для directory v1/v2 и clock; открытие schema-v1 файла новой
  реализацией; побитовые крайние значения и residual round trips.
- Инъекция SQL-ошибки в публикацию откатывает уже выполненные записи payload,
  удаление head, allocation state и group publication.
- Подпроцесс записывает head или sealed group и выходит без Close; другой
  процесс открывает файл и получает прежние значения. Выход происходит после
  завершённого commit, не внутри каждого возможного шага COMMIT.
- Гонки Ingest/Maintain/retention/Read, stale candidate, partial retention,
  clock ownership, граница watermark, ограничения и cancellation.
- Полная загрузка Alibaba/TSBS через публичный API, Close, Open и побитовая
  проверка всех возвращённых сэмплов, а не выбранного окна.
- CGO-free stripped linux/amd64 probe с используемым metrics API:
  8175776 байт, 6668288 байт сверх пустого baseline.

Это локальные проверки незакоммиченного состояния. Они не равны свежему CI на
macOS/Windows/Linux и не доказывают отсутствие race за пределами тестовых сценариев.

## 6. Как выполнялась проверка engine на корпусах

Тест `metrics/TestCorpusThroughPublicStore` использует те же нормализованные
JSONL, что и предыдущие сравнения. Он не создаёт готовые payload напрямую:

```text
разбор одной серии
→ Ingest чанками по 7681 точке
→ Maintain после каждого чанка
→ Close
→ размер реального файла
→ Open
→ Read каждой серии
→ сравнение каждого timestamp и IEEE float bit
```

Retention 100 лет сохраняет исторические timestamps; max head/batch — 8192;
lateness — 0. Ряды в этом сравнении регистрируются как gauge, как в исходном
storage harness; counter semantics дополнительно проверены отдельными тестами.
Последний sample и недостаточный для packing хвост остаются изменяемыми.

Диагностическое время input parsing + ingestion + maintenance составило около
73 секунд на Alibaba и 41 секунды на TSBS; reopened parsing + read + validation
около 3.1 и 2.5 секунд. Это не чистые ingest/s и query latency и не сравнение
CPU с другими engines. Прогоны не выполнялись как изолированный нагрузочный тест.

Воспроизведение после подготовки JSONL существующими bench runners:

```powershell
$env:TINYSTORE_JSONL = '<corpus-directory>/series.jsonl'
go test ./metrics -run '^TestCorpusThroughPublicStore$' -v -count=1
```

Для чисел, сопоставимых с отчётом, запускать Go 1.27.1 в Linux-контейнере с
репозиторием и корпусом в mounts. Обычный запуск тестов этот корпусный тест
пропускает, если переменная не задана.

## 7. Что означает bit-exact у конкурентов

- TinyStore engine в новых прогонах проверен на обоих полных корпусах.
- VM в прежнем Alibaba-прогоне вернула все значения побитово точно.
- VM на прежнем TSBS-прогоне изменила 147751 из 151200 проверенных float-значений.
  Поэтому точность нельзя переносить с Alibaba на произвольный float workload.
- Prometheus на TSBS проверен целиком; на Alibaba — указанное двухчасовое окно
  из 468470 samples по 1240 series. Не следует писать, что на Alibaba для него
  выполнена полная побитовая выгрузка.

## 8. Следующий приоритет

Первый следующий этап — packed durable head с теми же Ingest/Read/frontier
контрактами. TSBS уже показывает конкретную стоимость текущего решения: 6.4 МБ
из 12.8 МБ файла. После него — registry/postings и групповая compaction при
постепенном поступлении данных.

Принимать улучшение следует по полному файлу **вместе с WAL, RSS и задержками**,
с сохранением exact reopen, late input, version/CAS и retention. Принудительно
запечатать unsafe head или исключить его из denominator/файла нельзя.

Только после этого имеет смысл обновлять публичный scoreboard против заново
запущенных VM/Prometheus с явной политикой кешей, retention и одинаковым режимом
загрузки. Сейчас честное достижение — рабочий защищённый первый metrics-срез и
перенос основных алгоритмов из исследовательских тестов, а не завершение всей
архитектуры и не воспроизведённая engine-победа над VM.

# Internal diagnostics without hot-path log spam — 2026-09-27

The [four-engine audit](readability-2026-09-27.md) found that background
failure logs lost their engine identity, a quarantined metrics series could
change state without an event, KV's joined maintenance error hid its phase,
and records counted drops without saying why. This round fixes those paths
and adds low-rate Debug summaries. Ordinary request errors still return to
the caller; normal samples, keys, queries and successful jobs do not each
make a log record.

## Background origin and the records self-log guard

`Store.EveryEngine(engine, name, interval, work)` runs engine callbacks with
the same `engine` attribute as `Store.Logger(engine)`. It replaces the
registrations for metrics, records, KV, jobs and blobs, including KV's
separate counter/renewal tasks and records' flush. Public `Store.Every`
continues to register application callbacks without an engine attribute.
The existing ten-minute repeated-error counting and recovery behavior do
not change.

`records.Handler` rejects its own `engine=records` events. It now sees that
attribute on records background failure and recovery, so those diagnostics
cannot enter its queue through the usual composed application logger.
An earlier synthetic probe showed the old event entering without the tag;
the new tests check both the engine attribute across failure/recovery and
the handler's rejection of a scoped Debug flush summary. This is a routing
fix, not a claim that the old code had an infinite recursive loop.

## State changes and summaries

Metrics emits Warn `series suspended` once after a new quarantine row
commits. The event carries a file-local `series_id`, phase and the bounded
reason stored for `ListMaintenanceFailures`; it does not add label values.
The isolated-retention/read/encode path logs after its own transaction;
batch publication collects suspended ids and logs them only after the whole
batch commits. Repeated maintenance of an already suspended series emits
nothing. The persisted failure list remains the way to retrieve details
after restart.

Background maintenance in all five engines emits one Debug summary when
Debug is enabled, with elapsed time, result counts and a failure flag.
Records' background flush emits a Debug summary with elapsed time and
appended/drop deltas. The delta fields are snapshots of process-wide
counters and may include concurrent direct calls. Manual `Maintain` and
`Flush` already return their results; the new summaries cover the store's
scheduled work. Debug attributes are not built when the level is disabled.

KV wraps each `Maintain` stage before joining its errors: counter flush,
renewal, branch clearing and expiry. A failed relaxed-counter flush also
names its bucket. The background Warn thus carries both the stage and bucket;
the same error still wraps its underlying cause for `errors.Is`.

Records now exposes `DroppedFull`, `DroppedInvalid` and `DroppedWrite` in
`Stats`; their sum is the existing `Dropped`. The three causes are a full
handler/Lines buffer, an invalid or out-of-window record, and a failed flush.
The close event and background flush summary include the breakdown.
The handler still never waits for queue space.

Root `Store.Close` emits Warn `store closed with errors` with the joined
error when an engine or directory lock did not close successfully. A clean
Close retains Info `store closed`. This avoids a success-looking final
event when the returned Close error was non-nil.

## Logging latency and data policy

The supplied `Options.Logger` is called synchronously. The application
chooses its handler's latency; TinyStore cannot make an arbitrary handler
nonblocking simply by receiving `*slog.Logger`. The built-in
`records.Handler` and `Lines` writer are the bounded, nonblocking paths.
`AGENTS.md` and [architecture](../architecture.md) now say that explicitly.

Background events retain the existing full error text and lifecycle paths;
KV's bucket names and records' stream names can be application data.
Metrics' new default quarantine event uses a bounded reason and file-local
id, not the whole label set. A support bundle must be reviewed for sensitive
data before sharing. `slog` events provide history and attribution;
investigating Go scheduling or blocking still needs a separately captured,
bounded execution trace/profile.

## Checks and remaining work

`task check` passed on Windows with `GOWORK=off`, `CGO_ENABLED=0`:
module tidiness, formatting, lint with zero findings, shuffled tests,
vulnerability scan and the cgo-free import probe. Focused gates exercise
engine attributes across a background failure and recovery, a committed
metrics suspension logged once without label values, one metrics Debug
summary, KV's stage/bucket error, all three records drop reasons, records'
self-log rejection, and a failed Close outcome. The existing engine and
snapshot tests passed as part of the full suite.

`go test -race -shuffle=on -count=1 ./...` passed in the Go 1.27 Linux
container after the example's worker counter was made atomic. The first
race run found that pre-existing example counter race; it was fixed and
the full race run repeated. The root module and modified benchmark modules
also passed their compile checks after `go fix` modernization; see
[the modernization round](modernize-2026-09-27.md).

Still open, intentionally: applied-migration Info events; a summary for
application-invoked maintenance when its caller does not retain the result;
structured job panic evidence (the stack is persisted with the attempt but
the counted warning has only the panic value); and a safe policy for
transient handler errors that later succeed. Adding a log for every retried
job would flood a busy queue. Broad per-request Warn logs for limits and
deadlines would duplicate returned errors and could expose keys; they need
a specific support requirement and bounded policy first. No generic
diagnostic-bundle or automatic runtime-trace capture was built here.

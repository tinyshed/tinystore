# Second corpus: TSBS DevOps, against VictoriaMetrics and Prometheus

Ryzen 7 7700, Windows 11 host, Docker linux/amd64, Go 1.27.1, SQLite driver
1.59.0, klauspost/compress 1.19.0. Base codec `9e34181` plus the grid model of
[the NAB grid run](grid-2026-09-21.md), which lives only in `spike/`.

## The corpus

[TSBS](https://github.com/timescale/tsbs), MIT, revision
`8323e59c74027b108f4ad5ec5d3e498b0101a02e`, `tsbs_generate_data` with:

```text
--use-case=devops --seed=123 --scale=20 --log-interval=10s
--timestamp-start=2026-01-01T00:00:00Z --timestamp-end=2026-01-01T07:00:00Z
--format=influx
```

453600 readings become **2020 series and 5090400 samples**: 4939200 integer
fields and 151200 float fields, nine measurement families, ten to fourteen
labels a series, a strict ten-second cadence with no gaps and no duplicates.
Every integer was checked to fit float64 exactly, so the corpus itself commits
to nothing an engine cannot represent.

`bench/tsbs` parses the line protocol once and writes the three inputs from
that one parse — a JSONL corpus that is also VictoriaMetrics' import body, an
OpenMetrics file for promtool's backfill, and the line protocol unchanged — so
the three engines receive the same samples rather than three similar ones.
It also checks that every value survives its own shortest text form, because
all three paths are text.

This is a synthetic corpus of real monitoring *shape*: cardinality, labels,
cadence, counters and gauges. Its float values come from divisions and have no
decimal structure, which makes it an adversarial case for the grid model and a
deliberate contrast with NAB.

## Absolute sizes

| Engine | Bytes | B/sample | Every float bit returned |
|---|---:|---:|:--|
| VictoriaMetrics, complete directory | 5484522 | 1.0774 | **no** |
| TinyStore, complete SQLite file | 5873664 | **1.1539** | yes |
| Prometheus, one compacted block | 8300769 | 1.6307 | yes |

Components, for a comparison of like with like rather than of totals:

| Part | Bytes | B/sample |
|---|---:|---:|
| TinyStore payload only | — | 0.5775 |
| VictoriaMetrics `data` only, no caches | 3642783 | 0.7156 |
| Prometheus chunks only | 7767210 | 1.5259 |
| Prometheus index | 533241 | 0.1048 |
| VictoriaMetrics caches | 1841731 | 0.3618 |

Among engines that returned every float bit, TinyStore is **29.2% smaller than
Prometheus**. TinyStore is 7.1% larger than VictoriaMetrics' complete
directory, and VictoriaMetrics did not return every bit.

Our codec is not what loses to VictoriaMetrics. TinyStore's payload, 0.5775, is
19% below VM's `data` files and 2.64x below Prometheus' chunks. What gives it
back is the SQLite envelope: 1.1539 − 0.5775 = **0.5764 B/sample of
non-payload**.

## VictoriaMetrics is not bit-exact here, and this run proves it

147751 of 151200 float values did not return bit for bit, with
`-precisionBits=64`. All 4939200 integers did. The NAB run could not say
whether that was storage or the JSON export's formatting. It is storage.

A query that reads below the export's precision:

```text
(mem_available_percent{hostname="host_0"} - 84.3923450913) * 1e12   →   0
```

The original value was `84.39234509132802`; the residue is not merely
unprinted, it is absent. Three crafted values, imported and queried back:

| Probe | Stored value | `== 0.3` | `== 0.30000000000000004` |
|---|---|:--|:--|
| `0.30000000000000004` | `0.3` | matches | does not match |

| Probe | Input | Returned |
|---|---|---|
| a | `1.23456789012345` | `1.234567890123` |
| b | `1.23456789012999` | `1.234567890129` |

VictoriaMetrics keeps a decimal approximation of about thirteen significant
digits. `0.30000000000000004` compares equal to the literal `0.3` and unequal
to itself, which no formatting layer can cause.

So `-precisionBits=64` does not mean float64 is stored unchanged, and the
earlier framing — "VictoriaMetrics' data plus metadata is 20% smaller than
TinyStore" — was measuring a smaller thing as well as a lossier one. The
comparison is still worth reporting; it is not a like-for-like storage
contest.

Prometheus, by contrast, returned **0 of 5090400 values changed**, checked
against the corpus over a full `promtool tsdb dump`. It is the only
bit-exact comparator in this run, and the one the contract should be measured
against.

## The grid model does not generalise off NAB

The decimal grid of the previous run was chosen in **87 of 22220 blocks**.

| Payload, B/sample | TSBS |
|---|---:|
| Existing codec plus wrapper | 0.5782 |
| Learned grid model | 0.5775 |

0.12%. On NAB the same model was worth 39%. The NAB win was a property of that
corpus — real gauges written with a fixed number of decimals — and not a
general improvement in how floats are represented. On integer telemetry the
existing integer path already does the work, and the model correctly declines.

This answers the question one corpus could not: `q[]` on NAB costs 1.77
B/sample because those NAB series carry that much information, not because the
integer representation is weak. Here the same representation reaches 0.58
B/sample on 5 million samples.

The scale search costs 1.75 s against 0.40 s for the plain codec over the whole
corpus, diagnostic timings in one run, for 0.12%. On a corpus shaped like this
the model should not be attempted at all beyond the first block of a series.

## Where TinyStore's 0.5764 B/sample of envelope goes

Per b-tree from `dbstat`, page size 4096, after a truncate checkpoint:

| Object | Bytes | B/sample | Unused |
|---|---:|---:|---:|
| payloads | 3493888 | 0.6864 | 342736 |
| blocks | 1134592 | 0.2229 | 138218 |
| registry_labels | 589824 | 0.1159 | 61220 |
| registry | 552960 | 0.1086 | 23938 |
| series_state | 61440 | 0.0121 | 4779 |
| series_due | 36864 | 0.0072 | 8608 |
| sqlite_schema | 4096 | 0.0008 | 3028 |

The label registry and its unique index together cost **0.2245 B/sample**, 19%
of the file. Prometheus' whole index costs 0.1048 for the same 2020 series.
That is not a fundamental cost: the prototype registry stores each label set as
JSON text with a unique index over that text, which is the laziest possible
posting structure. It is the largest single addressable item this run found.

The blocks table costs 0.2229 B/sample, 51 bytes for each of 22220 rows. The
payloads table costs 0.1089 above the payload itself, mostly page slack. The
five small objects are 0.1447 together and shrink per sample as the file grows,
unlike on NAB where 24 series made them an artifact.

## Incremental BLOB reads revive grouping

[The NAB grid run](grid-2026-09-21.md) retired payload grouping because a
16-block group materialised 3662 bytes in Go to answer a 186-byte point read.
SQLite can read a byte range of a BLOB without materialising it, and
`modernc.org/sqlite/lib` has the whole translated API —
`Xsqlite3_blob_open`, `_read`, `_reopen`, `_bytes`, `_close`.

The driver does not expose it. `conn.db uintptr` and `conn.tls *libc.TLS` are
unexported, so `(*sql.Conn).Raw` hands over a `*conn` whose handle can only be
read by reflection. `bench/blob` does exactly that, and lives in its own module
because importing `modernc.org/libc` into the root module would fail
`TestTheModuleCarriesOnlyTheEngine`.

40000 microblocks of 210 bytes, page size 4096, page cache 2 MiB, 4000 point
reads per row, on a connection that did not write the file:

| Group | Rows | File bytes | `SELECT` ns | Ranged ns | `SELECT` B | Ranged B |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 40000 | 9134080 | 8615 | 1197 | 210 | 210 |
| 2 | 20000 | 9134080 | 8055 | 1246 | 420 | 210 |
| 4 | 10000 | 10272768 | 9041 | 1231 | 840 | 210 |
| 8 | 5000 | 10272768 | 8541 | 1272 | 1680 | 210 |
| 16 | 2500 | 10272768 | 9125 | 1315 | 3360 | 210 |
| 64 | 625 | 8544256 | 13559 | 2146 | 13440 | 210 |

Every one of the 4000 windows per row was compared with the same window of the
whole BLOB and matched, in all six layouts. A timing for bytes nobody checked
would not be a result.

The ranged read materialises 210 bytes at every group size, and its latency is
nearly flat from group 1 to group 16: 1197 ns to 1315 ns, **10% for a group
sixteen times larger**, where the whole-BLOB read materialises 16x the bytes.
Group 64 breaks the pattern at 2146 ns, because 13440 bytes exceeds a 4096-byte
page's local payload and the row moves onto overflow pages.

**The 7x gap between the two columns is not a bytes result.** `database/sql`
adds statement preparation, binding, row scanning and an allocation per read,
and the ranged path is a direct call. What this run establishes is the slope,
not the intercept: materialisation grows linearly with the group while the
ranged read does not.

Note also that the file is not monotonic in the group size here either — 9.1 MB
at group 1 and 2, 10.3 MB at 4, 8 and 16, 8.5 MB at 64 — on incompressible
random bodies. Grouping still has to earn its storage win separately; what
changed is that its read penalty is no longer the reason to refuse it.

## Not measured

Ingest throughput for any engine, WAL behaviour, retention, crash recovery,
cold reads, query latency beyond a warm point read, RSS, and Prometheus or
VictoriaMetrics under a live scrape rather than a bulk import. The Prometheus
figure is one block produced by `promtool` with `--max-block-duration=24h`,
which is not the same thing as a block its own compactor chose; letting its
background compactor run was rejected because Prometheus scrapes itself and
its own metrics grew the directory while being measured. The VictoriaMetrics
figure follows `force_flush`, an asynchronous `force_merge` and a graceful
shutdown, and is not a certified compaction optimum.

The reflection in `bench/blob` reads unexported driver fields and converts a
`uintptr` to `unsafe.Pointer`, which `go vet` flags. It is a feasibility probe,
not a design: the supported version of this is an upstream addition to
`modernc.org/sqlite` exposing a blob handle, and nothing in TinyStore should
depend on the field names of somebody else's struct.

## Reproduce

```powershell
./bench/run-tsbs.ps1
```

The script pins the TSBS revision, generates the corpus, converts it, measures
TinyStore, then VictoriaMetrics and Prometheus in containers, and checks each
engine's round trip against the corpus. The BLOB probe is separate:

```powershell
docker run --rm -v <repo>:/src -v dashbin-gocache:/go -e GOCACHE=/go/build-cache -e GOMODCACHE=/go/mod-cache -w /src/bench/blob golang:1.27 go run . -microblocks=40000 -runs=4000 -cache=2048
```

New code: `bench/tsbs`, `bench/blob`, `spike/tsbs_spike_test.go` and
`spike/engines_spike_test.go`. No root dependency and no released format
changed. `task lint`, `task test`, `task vuln`, `task fmt` and `task tidy`
pass; `task size` reports 2392 KiB with 920 KiB from the import, unchanged.

The script was run end to end on a freshly generated corpus. TinyStore's
5873664 bytes, Prometheus' 8300769, the 147751 VictoriaMetrics values that
changed and Prometheus' zero all reproduced exactly. VictoriaMetrics'
directory came back 5483810 bytes against 5484522, a difference of 712 bytes
or 0.013%: its merge is asynchronous and its cache files are not byte
deterministic, so that figure reproduces to about a hundredth of a percent
rather than exactly.

The runner builds docker's argument list as an array. Inline, PowerShell
splits `-in=/out/x.csv` into `-in=/out/x` and `.csv`, which silently strips the
extension from every path-shaped flag.

# The kv engine against hand-written tables and its prototype — 2026-09-26

The kv engine, built to [docs/kv.md](../kv.md), measured by `bench/kv` on its
five cases and on bare reads and writes. Each case runs twice on identical
input in the same run: through kv, and through the tables an application
keeps without it, in `sql/app.db` through `sqldb`, each write a transaction of
its own. Before measuring, every implementation answers the case's script on
a moved clock, and a phase that breaks a promise (a code taken twice, an event
handled twice, a count or a save lost) fails the run; none did.

106.

## What the numbers say

- **A write is an fsync, and grouping is what pays.** Alone, kv and the table
  both write about 360 a second in the container and 1,550 on the production
  host: one fsync each. From 8 goroutines on, kv commits the writes waiting
  together and the table cannot: 43,002 against 375 at 512.
- **The engine holds its prototype.** Written the way the mechanics round
  wrote them, new users in order, grouped Sets hold 358, 1,603, 10,029 and
  43,002 a second at 1, 8, 64 and 512 goroutines, against 333, 1,549, 9,894
  and 53,338. At 512 the engine is 19 % short: each write also reads its row
  and writes the revision's, where the prototype wrote the revision once a
  group.
- **Where a write lands matters as much.** Users at random scatter the
  inserts over the tree, every commit touches more pages, and the same Sets
  hold 17,358 a second.
- **Reads are faster than the prototype's.** The mark of a large `Clear`,
  checked in every statement that finds live rows, costs a read nothing
  measurable: 289,717 hits a second at 8 goroutines against the prototype's
  244,127.
- **Counters in memory are a hundred times the table.** A `LoseAtMost`
  counter's Add returns in 8 to 20 µs at the median; the table's commits each.
- **Sessions are where kv's model shows most.** The table renews a stale
  session inside the request, a commit each; kv's `Sliding` renews it with the
  flush a second later. The price is kv's contract: a crash forgets the
  renewals of the last second.
- **The file.** A session costs 231 bytes a row in `kv.db` against 177 in the
  table, 30 % more: kv's path carries the owner's and key's marks, and its
  expiry index repeats the path.

## The comparison is not only group commit

`sqldb` prepares its SQL on every call, reads inside a transaction, through
four connections; kv reads through eight, prepared, without one. The gap in
reads mixes those; the gap in writes is the commit.

Its reads are below the prototype's on the same host, and its writes at 512
too; one run of each, on a host whose load is not ours, does not separate the
engine from the neighbours.

## Environment and reproduction

- The engine at `64c43c9`, the harness at the commit adding this report.
- AMD Ryzen 7 7700, 8 cores / 16 logical processors, NVMe; Docker Desktop
  29.6.2 on WSL2, `golang:1.27` image running the harness built with go1.27.1
  for linux/amd64, the stores on a named volume. `modernc.org/sqlite` v1.59.0.
- Every phase: 3 s, its own store, 100,000 keys prepared (1,000,000 for
  reads), the table's first.

```sh
cd <repo>/bench/kv && GOWORK=off CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o <bin>/kv .
docker run --rm -v <bin>/kv:/kv:ro -v <volume>:/perf golang:1.27 sh -c '
  for st in sessions links attempts flood claims drafts writes; do
    /kv -stage $st -dir /perf/$st -keys 100000 -phase 3s -workers 1,8,64,512; done
  for st in hits misses; do
    /kv -stage $st -dir /perf/$st -keys 1000000 -phase 3s -workers 1,8,512; done'
```

The random-user writes ran before the stage wrote in order, from the same
harness otherwise; the production host ran the same binary, reads at 8
goroutines only.

## What this leaves

- **A write's two extra statements.** Reading the row is how `IfVersion`, the
  kept expiry and a spilled value are decided; the revision could be written
  once a group, as the prototype did, for about a fifth more at 512.
- **Scattered inserts.** Sessions of random users hold a third of in-order
  ones; a larger writer cache is the first thing to measure.
- **The production host's reads**, below the prototype's there, in a second
  run on a quiet hour.

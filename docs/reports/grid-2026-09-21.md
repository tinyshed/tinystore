# Residual modes, rational grids, and where the bytes actually are

Same pinned NAB subset and normalization as [the first corpus run](nab-2026-09-21.md)
and [the decimal model run](model-groups-2026-09-21.md): 24 series, 137256 samples.
Ryzen 7 7700, Docker linux/amd64, Go 1.27.1, SQLite driver 1.59.0,
klauspost/compress 1.19.0. Base codec `9e34181`, production codec untouched.

Every number below comes from a run that reconstructs each block and compares
IEEE bits, and the SQLite runs read the whole dataset back and compare every
timestamp and float bit before any size is reported.

## What moved

The decimal model of the previous run encoded its exact corrections as signed
varints with an optional zstd pass. This run replaces that single choice with
six residual modes — all-zero, nonzero bitmap plus sign bits, nonzero bitmap
plus fixed-width zigzag, fixed-width zigzag over everything, gap-coded sparse
positions, and the previous varint with and without zstd — and keeps whichever
is smallest, tagged in one byte. It also extends the grid search from ten
decimal scales to sixteen.

| Payload, B/sample | Previous run | This run |
|---|---:|---:|
| Existing codec plus wrapper | 3.9124 | 3.9124 |
| Best scale independently per block | 2.4524 | **2.3544** |
| Scale learned from the first block of a series | 2.4640 | **2.3685** |

| Whole SQLite file, ungrouped | Previous run | This run |
|---|---:|---:|
| Bytes | 471040 | **425984** |
| B/sample | 3.4318 | **3.1036** |

The file fell 9.6% while the payload fell 3.9%. That gap is page packing, not
compression: about 13100 payload bytes disappeared and 45056 file bytes followed,
because the smaller rows crossed a step in how many fit on a 4096-byte page.
It is the same mechanism that has made payload wins vanish before, running the
other way for once, and it is a property of this corpus's row sizes rather than
a repeatable exchange rate.

Learning the scale from a series' first block costs 0.6% of payload against
searching every block, and the whole learned search over the corpus takes
58 ms of diagnostic encoding time.

## Grouping is no longer worth anything

The previous run's best prototype was 438272 bytes and needed 16 independently
decodable microblocks per physical row. The ungrouped file above is smaller than
that. Sweeping the group width over the same builder:

| Group | Learned file bytes | B/sample | Point read, bytes fetched | Day range, bytes fetched |
|---:|---:|---:|---:|---:|
| 1 | 425984 | 3.1036 | 186 | 392 |
| 2 | 458752 | 3.3423 | 502 | 1038 |
| 4 | 503808 | 3.6706 | 987 | 987 |
| 8 | 430080 | 3.1334 | 1864 | 1864 |
| 16 | 425984 | 3.1036 | 3662 | 3662 |
| 32 | 434176 | 3.1633 | 3864 | 3864 |

Group 1 and group 16 produce byte-identical files, and the widths between them
are worse, by up to 18%. There is no knee to find because there is no curve:
the storage differences here are page-packing steps, and the ordering is not
monotonic in the group width. The control encoding shows the same shape, with
group 2 at 835584 bytes against group 1 at 700416.

This retires the previous run's "grouping 16 brings the total reduction to
37.4%". That 7% was an alignment accident of the larger payloads, not a
property of grouping, and it does not survive a payload this size. Grouping
still shortens a whole-file summary scan, 31 us to 8 us — but a summary scan
is served by the block metadata, which can be grouped without grouping payload
bodies, and that is now the only version of the idea with a measurement
behind it.

Point-query latency did not separate the layouts: every width sat between 21
and 25 us, warm, within run-to-run noise. The bytes-fetched column is Go
materialization, not disk traffic, and cold reads were not measured.

## Rational grids: a negative result

Generalising the grid from `q / 10^k` to `q x 1/d` was tested with 39 further
denominators: every power of two to 2^24, and 3, 6, 7, 9, 12, 24, 30, 60, 300,
360, 3600, 86400, 30000, 60000, 1024000, 3e5, 3e6, 6e4, 6e5.

| Grid set | Payload, B/sample | Search time |
|---|---:|---:|
| 16 decimal scales | 2.3544 | 682 ms |
| plus 39 rational denominators | 2.3492 | 2526 ms |

0.22% for 3.7x the search. The non-decimal denominators won 21 of 580 blocks,
the best of them 1024000 and 3600 with seven blocks each. On this corpus the
hypothesis that real metrics arrive on non-decimal grids is not supported.
It is one corpus of machine telemetry, so this rules the idea out of the next
round rather than out of the format.

The related suspicion about scale 8 is also settled, and it is dull: the values
selecting it are written with eight decimals, for example `69.88083514`.
Nothing about float representation is involved.

## Where the remaining bytes are

The payload divides, per sample over all 137256 samples:

| Part | B/sample | Share |
|---|---:|---:|
| Quantised integer base stream | 1.7730 | 75.3% |
| Blocks no model won, at the plain codec | 0.4058 | 17.2% |
| Exact residuals | 0.1102 | 4.7% |
| Timestamps and framing | 0.0654 | 2.8% |

The residual stream is finished. 86% of residuals are exactly zero, 11% are a
single unit in the last place, and the whole stream is under a ninth of a byte
per sample; no further work on it can win more than 0.11 B/sample in total.
The blocks that fall back to the plain codec are not an opportunity either — they
cost about 1.57 B/sample among themselves, below the 2.63 B/sample the model
blocks cost, so they are the cheap blocks and the model correctly declines them.

The base stream is the payload. Against the current Simple8b-or-Huffman packing
at 1.7730:

| Value-stream candidate | B/sample |
|---|---:|
| Current codec | 1.7730 |
| Patched frames of 64 | 1.7488 |
| Patched frames of 128 | **1.7452** |
| Patched, better of first and second difference | 1.7487 |
| Varint plus zstd | 1.8839 |
| A single fixed width per block | 1.9596 |

Patched frames — a fixed width per frame with wide values lifted out as an index
and a full value, so one outlier cannot widen its neighbours the way a Simple8b
selector does — are worth 1.6% of the value stream, about 1.2% of the payload.
Second differences add nothing. This is measured as a size, not implemented:
no decoder, no fuzzing, no encode cost.

## The entropy floor was an artifact, and it matters

A first pass reported the order-0 entropy of the delta alphabet as 0.6326
B/sample against the codec's 1.7730, which reads as a 2.8x headroom. It is not
one. Over the model blocks, 101419 deltas use 79144 distinct symbols, so the
entropy figure hides the whole stream inside an alphabet it does not charge
for. Charging for it naively — one varint per distinct symbol — gives 2.3556
B/sample, which is worse than what the codec already spends.

So there is no symbol-coding win waiting on this data. Huffman, ANS and any
other order-0 coder over the delta alphabet are ruled out here for a reason
that is measurable rather than aesthetic, and the 1.6% from patched frames is
the realistic remainder of the value stream.

## The file divides like this

Learned model, ungrouped, per b-tree from `dbstat`, at each page size. Payload
rows average 560 bytes.

| Page size | File bytes | B/sample |
|---:|---:|---:|
| 1024 | 501760 | 3.6557 |
| 2048 | 446464 | 3.2528 |
| **4096** | **425984** | **3.1036** |
| 8192 | 442368 | 3.2229 |
| 16384 | 507904 | 3.7004 |

At 4096 the division is:

| Object | Bytes | B/sample | Unused |
|---|---:|---:|---:|
| payloads | 360448 | 2.6261 | 28336 |
| blocks | 45056 | 0.3283 | 8805 |
| registry | 4096 | 0.0298 | 1763 |
| registry_labels | 4096 | 0.0298 | 1764 |
| series_due | 4096 | 0.0298 | 3777 |
| series_state | 4096 | 0.0298 | 3440 |
| sqlite_schema | 4096 | 0.0298 | 3028 |

The payload is 2.3685 B/sample and its table is 2.6261: 0.2576 B/sample of row
overhead and page slack, most of it the 28336 unused bytes. The blocks table is
0.3283 B/sample, 77.7 bytes for each of 580 rows, which is what nine columns of
eight-byte integers and reals cost. The five small objects together are
0.1491 B/sample and are an artifact of 24 series in a tiny file; they do not
grow with samples and would amortise away at any real cardinality.

Page size 8192 stores the payload most densely, 2.5664 B/sample, and still
loses overall because every small object then costs a full 8 KiB page. 4096 is
the knee, and it is the SQLite default.

## What this does and does not say about VictoriaMetrics

Against the same measured run in [the first corpus document](nab-2026-09-21.md),
whose caveats all still apply:

| Complete deployment footprint | B/sample |
|---|---:|
| TinyStore, learned model, ungrouped | 3.1036 |
| VictoriaMetrics directory after shutdown | 4.3426 |

| Core stored data and metadata | B/sample |
|---|---:|
| TinyStore, same file | 3.1036 |
| VictoriaMetrics data plus metadata | 2.5752 |

TinyStore is 28.5% smaller than VM's complete directory and 20.5% larger than
its data and metadata without caches. Neither number is an engine ranking. The
VM HTTP round trip changed 13872 float bit patterns, so the precision contract
is not equivalent, the corpus is one small set of machine telemetry, and the
TinyStore file is a storage prototype with no mutable head, no general label
postings, no ingest concurrency and no retention workload in it.

## Not measured

Ingest throughput, WAL behaviour under incremental ingest, retention, crash
recovery, mixed insertion order, cold reads, a bounded compactor, counter
summary composition, and any corpus other than this one. The residual modes
and the grid framing have checksums but have not been fuzzed or hardened
against malformed input; the model parser is prototype code in `spike/` and
no released format changed.

The scale-learning rule here is the previous run's: the first block of a series
searches, later blocks try that scale and keep the plain codec if it is smaller,
and a series whose first block declines the model declines it thereafter. No
probing of neighbouring scales and no re-learning were measured.

## Reproduce

```powershell
docker run --rm -v <repo>:/src -v <corpus>:/corpus -v tinystore-gocache:/go -w /src -e TINYSTORE_CORPUS=/corpus -e GOCACHE=/go/build-cache golang:1.27 go test ./spike -run '^TestGridDiagnosis$|^TestBaseStreamHeadroom$|^TestDeltaAlphabetIsMostlyDistinct$|^TestGroupSizeKnee$|^TestGridFileDivision$' -v -count=1
```

Fetch the pinned corpus first with `bench/run-nab.ps1` if needed. The new code
is `spike/grid_spike_test.go`, `spike/base_spike_test.go`,
`spike/floor_spike_test.go`, `spike/knee_spike_test.go` and
`spike/pages_spike_test.go`. No dependency and no released format changed.

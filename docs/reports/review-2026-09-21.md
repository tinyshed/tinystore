# Review of the overnight measurements

Reviewed base: `9e34181`. Only the codec is implemented; the SQLite layouts and
retention routines below are prototypes, not a working store. The night log
is evidence of that work, not an instruction for this review.

The overnight improvements are real on their fixtures. The conclusions that
float compression is exhausted and a 1300-byte block target should be universal
do not follow from the measurements. Both have counterexamples below.

## Reproduction and limits

21 September 2026, Ryzen 7 7700, Docker `golang:1.27`, Go 1.27.1 linux/amd64,
modernc SQLite v1.59.0, klauspost/compress v1.19.0. Commands from the repository:

```powershell
docker run --rm -v <repo>:/src -v tinystore-gocache:/go -w /src -e TINYSTORE_SPIKE=1 -e GOCACHE=/go/build-cache golang:1.27 go test ./spike -run '^TestReview' -v -count=1
docker run --rm -v <repo>:/src -v tinystore-gocache:/go -w /src -e GOCACHE=/go/build-cache golang:1.27 go test ./...
./bin/golangci-lint.exe run ./spike
```

The new experiments are in `spike/review_spike_test.go`. No production codec,
schema, or format has been changed. Byte transforms and exceptions are size
prototypes with bitwise reconstruction checks, not new supported encodings.
They include an explicitly charged framing budget. They do not yet have a
corruption-resistant parser or representative encode/decode latency results.
All six review experiments and `go test ./...` passed in the Linux container;
`golangci-lint run ./spike` passed on Windows. Full `task check` was not run.

## 1. The reported float floor is not an entropy bound

`TestHowMuchOfAFloatBlockIsActuallyShared` counts positions that change anywhere
in a block and labels their count divided by eight `floor>=`. This counts
variable bit positions, not independent information. Even a sequence alternating
between two complementary bit patterns changes every bit and remains cheap to
encode. The method cannot establish the claimed 6.404 B/sample lower bound.

Measured on identical inputs in one run: 256 independently encoded blocks of
240 samples, existing `adaptiveSamples` generator and seeds 0..255. Every
candidate is reconstructed and compared bit for bit. The external first value
and time head are shared on both sides, exactly as in the current codec.

| Value encoding | Noisy walk, B/sample | Sine, B/sample |
|---|---:|---:|
| Current codec | 6.5112 | 7.8375 |
| Byte transpose, then zstd | 6.2653 | 6.9667 |
| First difference of IEEE bit words, zigzag, byte transpose, zstd | 6.1582 | 6.5958 |
| Second difference of IEEE bit words, zigzag, byte transpose, zstd | 6.1583 | 6.1667 |
| First difference of IEEE bit words, arbitrary width, one group | **5.7232** | 8.0125 |

Transpose candidates pay eight envelope bytes. Bit packing pays nine framing
bytes plus width and trailing-zero fields for each group. Subtraction is
modular integer subtraction of the bit words, never subtraction of float
values; reconstruction reverses every operation. No bits are rounded away.

The last candidate saves 12.1% of noisy payload against the current codec on
this input. This is not a whole-file saving: crossing SQLite packing thresholds
must be measured separately. The sine and random-bit losses show why this must
be another candidate selected by final encoded size, not a replacement.

**Decision:** a small arbitrary-width packer is worth a measured implementation
before searching for a more elaborate entropy coder. A corpus decides how
often the opportunity occurs; it is not needed to disprove the claimed floor.

## 2. One decimal exception can cost almost six times the block

`encodeScaled` rejects an entire block when any value cannot round-trip at an
allowed decimal scale. On the existing 240-sample temperature fixture, replacing
sample 120 with one exceptional value gives:

| Exception | Current block | Patched decimal base plus exact exception |
|---|---:|---:|
| NaN with payload `0x1234` | 413 B | 72 B |
| Pi | 417 B | 72 B |

The size prototype substitutes the preceding value in the base stream and
restores the exact exception after decoding. The 72 B includes the current
base envelope plus one mode byte, one count byte, one position byte and eight
literal value bytes. A final format must checksum the exception records too.
The decoder check reconstructs every original timestamp and float bit.

**Decision:** promote exceptions in the scaled path. Keep a bounded exception
count and choose the completed block against existing encodings. The first
sample, many exceptions, a scale change and malformed exception records need
coverage before adoption. This does not prove a sixfold improvement on a whole
corpus; it proves a large failure of the all-or-nothing choice on affected blocks.

## 3. The reported mixed file does not exist

`reportDense` averages four separate database measurements. That is a useful
equal-weight class score, but it is not the size of a file containing all four
classes. Variable-size rows share pages in that file.

`TestReviewActualMixedFile` puts all four classes in one database: 250 series
per class, 2400 samples per series, 2.4 million total. Both policies receive
exactly the same timestamp/value samples assigned to the same series. Each
class uses a deterministic stream from `adaptiveSamples`, split into those
series. Payload writes interleave classes; schemas retain the same summaries,
series state and due index. This is a controlled layout counterexample, not a
representative corpus or a steady-state ingest benchmark.

| Policy | Whole prototype file, B/sample | Payload, B/sample |
|---|---:|---:|
| 240 samples for every class | **2.4047** | 1.8721 |
| 200 for noisy float, 240 for the other classes | **2.7102** | 1.8688 |

The second policy increases the file by 12.7% despite reducing payload. Unused
bytes in the payload b-tree rise from 10.3% to 20.9%. Both files were measured
after a truncate checkpoint; page_count times page_size equals dbstat totals
and freelist_count is zero. These files do not contain a registry or mutable
head, and are not the footprint of a complete engine. WAL was not measured.

The existing final-night test also chooses each class's sample count from one
seed and uses it for every block; it does not exercise a running byte-threshold
closer on each actual block.

**Decision:** retain a byte budget as a safety limit, but do not canonize 1300
as a universal packing optimum. Benchmark actual mixed files, insertion order,
bounded write batches and retention reuse. A promising separate experiment is
arranging immutable payloads within a bounded batch by size, without changing
their logical series/time identity or the unit decoded by a query.

## 4. Retention has both a scaling problem and a reactivation bug

`sweepBySeries` computes `min(end_ts)` over the entire retained history of a
series. The clustered key is `(series_id,start_ts)`, not `end_ts`. Both delete
statements likewise filter on the unindexed end timestamp. The night fixture
has only ten blocks per dense series and cannot expose the scaling cost.

For the next-expiry lookup alone, 100 warm queries per case in one run:

| Retained blocks per series | `min(end_ts)` | Ordered first block |
|---|---:|---:|
| 10 | 8.4 us | 7.3 us |
| 1000 | 72.4 us | 6.8 us |
| 10000 | 625.8 us | 7.2 us |

The alternative is `select end_ts from blocks where series_id=? order by
start_ts limit 1`. It is valid because sealed blocks of a series do not overlap
and their end timestamps have the same order as their starts. About 87x applies
only to this lookup at 10000 blocks, not the entire GC pass.

A correct prefix sweep should fetch a bounded ordered prefix, stop at its first
unexpired block, delete payloads and block keys together, and obtain the next
expiry from the first survivor. This makes work depend on expired blocks rather
than the whole retained history. Do not restore the global per-block expiry
index merely to hide this query problem.

Separately, `upsertState` uses `min(next_gc_ts, excluded.next_gc_ts)`. After GC
empties a series and sets its next expiry to NULL, a newly inserted block leaves
the field NULL. The series remains outside `series_due`. The test reproduces
this in all three cases. Use an explicit NULL branch, and add an
empty → new block → due → collected lifecycle gate to the eventual store.

## 5. Moving the first value into REAL breaks the exactness boundary

The codec's head/body split is valid, but `first real` is not an exact bit
container. Through the actual SQLite driver:

| Input first value | Read from REAL | Current body decoded with read head |
|---|---|---|
| Negative zero | Positive zero | CRC failure |
| NaN with payload `0x1234` | NULL | CRC failure if mapped to zero |
| 1.0 | 1.0 | Success |

Storing `int64(math.Float64bits(value))` in an INTEGER and reversing that cast
preserves both exceptional values; the test verifies the complete codec round
trip using that head. An eight-byte BLOB also supplies exact storage. The
design already warns about numeric head storage in research.md; the new
external codec head makes this a concrete integration blocker.

**Decision:** choose an exact persisted first-value representation before
adopting the row layout. Charge its cost: storing every first value as eight
literal bytes loses the compact numeric-integer representation in ordinary blocks.
A tagged numeric/exception representation is an alternative to measure.
CRC detects a changed head; it cannot recover the original value.

SQLite documents the internal integer storage of integral REALs in
[type affinity](https://sqlite.org/datatype3.html#type_affinity).

## 6. The next structural candidate: separate storage grouping from decoding

The integer payload is near the order-0 entropy of the synthetic delta
alphabet. That part of the night is justified. But a 240-sample decode does
not require one SQLite row for every independent block.

A candidate for the next layout experiment is a bounded group of independent
microblocks with a small directory of offsets and per-microblock summaries.
The directory must be readable without decompressing sample streams. A narrow
query decodes only the microblocks it intersects. Physical grouping can then
amortize keys, record headers and repeated summary structure without silently
raising the sample decode limit.

This is unmeasured. It must beat the current separate metadata/payload layout
on whole-file size, actual range queries, summary scans, WAL and retention.
Grouping raw streams into one zstd frame would invalidate the idea. A group
also creates physical retention slack and read amplification, which must be
charged even when decoding remains small. Do not implement a second page
manager before a small spike shows a material gain.

## Suggested order

1. Correct the exact head boundary and the NULL reactivation case before the
   store adopts these prototypes.
2. Replace the GC history scan with a bounded ordered prefix; retain lifecycle
   and crash-atomicity checks.
3. Implement and measure decimal exceptions and an arbitrary-width residual
   candidate, selecting on completed encoded size and measuring decode cost.
4. Replace the averaged mixed score with an additional real mixed-file suite
   before setting a universal byte threshold.
5. Use a real corpus to rank those gains; run packed-tail and grouped-metadata
   experiments against the workloads they are meant to improve.

The scan and encoding opportunities above are already demonstrated. Corpus
work remains necessary for prioritization and any comparison with another
engine, but it is not a prerequisite for fixing the measured blind spots.

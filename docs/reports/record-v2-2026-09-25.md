# Record segments in event-time order: v2 codec, layout and search — 2026-09-25

The [reconstruction round](record-reconstruction-2026-09-25.md) reached 9.8304
bytes per record in a closed SQLite file, with an encoder of 965 records/s and
a whole-segment zstd envelope no query can read part of. This round settles
three decisions and replaces the encoder:

1. **Order.** A segment stores one stream's records sorted by event time;
   equal times keep their arrival order. Arrival order between different times
   is not kept: concurrent producers make it noise, and it costs bytes.
2. **Contexts.** Each segment keeps its context dictionary, in its own row.
   A store-level registry waits for a real corpus that needs it.
3. **Layout.** A segment row holds what its blocks share; each block of at most
   1024 records is its own row with a column directory and checksum; trace ids
   get a bloom row per block. There is no envelope over the whole segment.

On one million `frontend` records the complete file is **7.8520 bytes per
record**, the encoder runs at about 480,000 records/s on one CPU, and a one
second query reads 2 of 977 blocks. `records/` itself is unchanged.

## Environment and reproduction

- Spike sources of commit `0f7500a`; every figure below was measured on it.
  Windows 11 Pro 10.0.26200, AMD Ryzen 7 7700, 8 cores / 16 logical processors.
  Go 1.27.1 windows/amd64, `modernc.org/sqlite` v1.59.0, `klauspost/compress`
  v1.19.0 (`zstd` at `SpeedDefault` with a 256 KiB window for text blobs, `fse`
  for small alphabets). One encoder and one decoder, no worker concurrency.
- Inputs: the fixtures of the earlier rounds (`recordFixture`,
  `recordStatefulFixture`, PCG seeds unchanged), 10,000 records each and one
  million for `frontend` and `backend`; the pinned GH Archive prefix of
  `bench/record-events-sha256.txt` as the real control.
- Every encoded segment is decoded and compared to its input in stored order;
  every query result is compared to a scan of the whole input. SQLite files are
  written in one transaction, vacuumed, and divided by `dbstat`. No WAL, head,
  retention or concurrent readers are included. Docker's Linux daemon was not
  used; nothing here is a Linux or throughput-under-load result.

## Why the previous encoder took ten seconds

A CPU and allocation profile of the previous `final` encoder on the frontend
fixture (`BenchmarkRecordThroughput/adaptive/encode`, `-benchtime=1x -cpu=1`
with `-cpuprofile` and `-memprofile`) attributes the time:

| Where | Share of CPU |
|---|---:|
| `predictRecordColumn`: eight references × dependency, recipe and numeric state, each encoding its exceptions with the full search | 76.0 % cumulative |
| `recordPackedNumbers`: a loop over every bit of every value | 34.9 % flat |
| `zstd.EncodeAll` on trial candidates | 21.9 % cumulative |
| bucket order and shared contexts, each re-encoding every block | 25.6 % and 23.3 % cumulative |

Of 15.94 GB allocated over the two profiled encodes, 0.84 GB were
`strconv` syntax errors from trying to parse text as numbers. On this fixture
the expensive families did not pay: they were built for `derived_fields` and
`stateful`. v2 keeps two of them, but runs a candidate only after the first 8
to 16 rows agree with it, and compares every other candidate by computed size
instead of compressing it.

## What the frontend fixture allows

The generator draws, per record, a session among 500, a uniform nanosecond
offset within one second, an element among 4, a URL among 3, `x < 1920`,
`y < 1080` and a 1-in-17 experiment flag; each session's context holds a
SHA-256-derived identifier. No codec can store less than this information
(`TestRecordV2FrontendFloor`):

| Column | Floor, arrival order | Floor, time order | v2, time order, 10,000 records |
|---|---:|---:|---:|
| time | 3.7372 (29.9 bits) | 2.7295 (Rice code on sorted gaps) | 2.7448 |
| context ids | 1.1207 | 1.1207 | 1.1288 |
| context dictionary, per 10,000 records | 0.7773 | 0.7773 | 0.8718 |
| x, y, element, URL, flag | 3.1114 | 3.1114 | 3.2644 with shapes |
| total | **8.7466** | **7.7390** | 8.0308 |

The arrival-order floor is why the previous file stopped at 9.8304: 87.5 KB
of irreducible payload still needs the 22 pages of 4 KiB its row used, so no
codec could have made that file smaller. Time order removes about 8 bits of
permutation per record here; that saving comes from the contract, not from
the codec. The measured time cost is a real Rice
code, so the time-order floor is an upper bound on the true entropy.

## The complete file

One million records, 1 KiB pages, time order unless stated. `dbstat` gives
allocated / payload / unused bytes; `sqlite_schema` and the empty bloom table
are omitted from the division below and included in the total.

| Input | Payload | Bloom | File B/record | Division |
|---|---:|---:|---:|---|
| frontend | 7.6906 | — | **7.8520** | blocks 7,254,016 / 7,179,905 / 33,207; segments 569,344 / 540,160 / 25,730; index 26,624 |
| frontend, arrival order | 8.7224 | — | 8.9272 | blocks 8,329,216 / 8,212,738 / 70,500 |
| backend | 19.2018 | 1.2500 | 20.7217 | blocks 19,338,240 / 19,219,959 / 28,216; blooms not shown |
| GH Archive, 4096 real events | 380.6729 | — | 386.2500 | blocks 1,575,936 / 1,559,611 / 9,392 |

The per-segment context dictionary costs 0.54 bytes per frontend record at
16,384 records a segment. On GH Archive v2 is 1.8 % larger than the previous
codec's 373.99 payload: large JSON values per column, compressed per block,
without the previous whole-segment envelope. Encoding one million records took
2.3 s for frontend and 1.3 s for backend, including sorting; writing them to
SQLite took 55 ms and 240 ms.

### Page size decides a tenth of the file

The same frontend records, divided by block size and page size:

| Records per block | 1 KiB pages | 4 KiB pages | 16 KiB pages |
|---|---:|---:|---:|
| 1024 | **7.8520** | 8.6016 | 9.1259 |
| 2048 | 7.7128 | 8.5811 | 9.0931 |
| 4096 | 7.6646 | 7.7005 | 9.0931 |

A row larger than a page keeps its last part on a leaf page: SQLite fills the
overflow pages completely and leaves the remainder, between 489 and 4061 bytes
at 4 KiB, local. A 7.3 KB block leaves about 3.2 KB local, one per leaf page,
and 10 % of the table is empty space. 4096-record frontend blocks happen to
end just past a page boundary and leave a few hundred bytes per row; that is
their size, not a property of the layout, and backend with 2048-record blocks
loses 4.4 % instead. 1 KiB
pages bound the remainder to 989 bytes for every size. Narrow queries ran at
the same speed with 1 KiB and 4 KiB pages; 4096-record blocks made them two to
four times slower because every candidate block decodes four times as many
records.

## Queries

One million records in 62 segments of 977 blocks. Each result was compared to
a scan of all input; bytes include segment rows and bloom rows fetched. Single
runs with a warm cache, not latency percentiles.

| Query | Rows | Segments | Blocks read | Blocks decoded | Bytes | Time |
|---|---:|---:|---:|---:|---:|---:|
| frontend, one second | 786 | 1 | 2 | 2 | 23,367 | 2.6 ms |
| frontend, `element = "buy"`, ten seconds | 1,989 | 2 | 10 | 10 | 90,703 | 6.0 ms |
| frontend, one session, one minute | 114 | 4 | 49 | 45 | 393,753 | 20 ms |
| frontend, one session, all time | 2,014 | 62 | 976 | 845 | 7,686,322 | 394 ms |
| backend, one second | 1,000 | 1 | 2 | 2 | 39,482 | 1.0 ms |
| backend, level ≥ 8, one minute | 3,750 | 5 | 59 | 59 | 1,160,291 | 30 ms |
| backend, one trace, all time | 1 | 6 | 6 | 1 | 1,368,982 | 8.5 ms |
| backend, one trace, a minute without it | 0 | 0 | 0 | 0 | 75,520 | 1 ms |

- Time and level prune through a covering index of `(first_at, last_at,
  levels)`; a block of 1024 frontend records spans about 1.3 s.
- A context value is found in the segment dictionaries and then in the
  context-id column; no per-record index exists. This fixture draws sessions
  uniformly over all time, so every block holds every session: the all-time
  query reads everything. Real sessions cluster in time.
- An attribute filter decodes one column per candidate block and rebuilds only
  the matching rows.
- The trace bloom, 10 bits per distinct id and 7 hashes, gave 5 false candidate
  blocks of 977. Reading all blooms costs 1.25 bytes per stored record once per
  query without a time bound.

## Bounds, integrity and gates

A segment holds at most 16,384 records and 4 MiB of input; a block 1024
records and 256 KiB. Shapes are limited to 64 per segment before records keep
their attributes as one serialized value, and to 1024 attribute columns;
contexts to 2^20 cells. Every segment row and block row carries a CRC-32; counts,
lengths, references, radix words, Rice streams, FSE expansion and text
expansion are bounded on decode. A prediction may reference only an earlier,
unpredicted column over the same rows. The decoder does not validate the JSON
of text values: an intact checksum over a valid encoding cannot produce
invalid JSON, and a damaged block is refused by its checksum first.

`TestRecordV2CorruptionIsRefused` changes every byte and truncates at every
length of a block and a segment row. `FuzzRecordV2Block` repairs checksums
before decoding and round-trips whatever decodes: 1,870,765 executions in 60 s
with four workers and no failure, and no input over the two-second guard.
Go's default input minimization stopped counting executions for tens of
seconds at a time, hence `-fuzzminimizetime=1x`. `golangci-lint run ./spike`
passed.

## Not measured, and what remains

- No durable head, ingest through the non-blocking handler, WAL growth,
  concurrent readers or peak memory. Segments are sealed from complete
  batches; a head that collects them is the next piece.
- The block index query scans every entry older than the requested end; at
  this scale that is 977 entries. A bound on block span, or a second index,
  is needed before it grows.
- Keyed numeric state, nested-JSON decomposition and a store-level context
  registry are not ported; `stateful` shows what the first two were worth.
- The fixtures are synthetic apart from GH Archive, which gained nothing from
  either codec. A real structured-event corpus remains the acceptance gate
  before engine integration.
